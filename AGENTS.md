# Chess Review — Agent Guide

## Project Overview
Browser extension (MV3) for Chess.com/Lichess game review with local Stockfish analysis.
Entrypoints: `popup.html` → `analysis.html` (review UI), `content.js` / `lichess-content.js` (page integration), `background.js` (service worker).
Optional Windows native engine: `native/` (Native Messaging host + bundled official Stockfish 19 exe).
The popup offers one board: **Live board** (`analysis.html#live`). `analysis.html#explore` still works as a URL but has no button any more — do not reintroduce one without asking.

## Commands
```bash
npm ci                    # install deps
npm test                  # node --test tests/*.test.mjs (jsdom + vm)
npm run lint              # scripts/lint.mjs (web-ext lint; stages a hardened Firefox profile)
npm run verify:engines    # verify bundled Stockfish WASM checksums
npm run build             # package Chrome + Firefox ZIPs + source snapshot to web-ext-artifacts/
npm run start:chrome      # web-ext run --target=chromium (dev)
npm run start:firefox     # web-ext run --target=firefox-desktop (dev)
npm run test:browsers     # real-browser smoke; honors CHROME_PATH / FIREFOX_PATH env vars
npm run test:native-host  # real-protocol test of the native host (Windows-only; skips elsewhere)
npm run perf              # engine-free vm benchmark (open/step/flush/save/sidebar medians); docs/PERFORMANCE.md
npm run update:dataset    # refresh the Lichess validation sample + lock (tools/calibration-experiments; not shipped)
node tools/calibration/reproduce-public.mjs   # offline replay of the public scoring models (no engine, no network)
```
CI gate (`.github/workflows/verify.yml`, ubuntu-24.04 + Node 22; `package.json` declares no `engines`): `npm ci` → `npm test` → `npm run lint` → `npm run verify:engines` → `node tools/calibration/reproduce-public.mjs`. Run that same order locally before pushing.

## Test Notes
- `tests/*.test.mjs` use Node's native test runner + JSDOM; one file = one suite (**68 suites**).
- Run one suite: `node --test tests/classification.test.mjs`.
- Helper `tests/helpers/app.mjs`: `app(t)` runs the real `analysis.js` in a vm context with browser APIs and `Engine` stubbed; `loadGame`/`branch`/`settle`/`fakeEngine`/`deferred` build state. Imports are stripped from the source, so extra globals go through `a.context.X`; `a.replace(name, fn)` stubs any internal function; `a.state` is the `S` object; `a.store` is the fake `storage.local`.
- Helper `tests/helpers/popup.mjs`: `popup(t)` runs the real `popup.js` against the real `popup.html` in JSDOM with only the browser boundary and the recent-games pager stubbed. It is async (the popup's own startup must settle) and asserts through the DOM + `storage.local`, because `popup.js` has no exports.
- The harness sets `BOOK = {}` and overrides `CALIB`, so classification is deterministic — pass book/calibration explicitly when a test needs it. Anything about the **public models** must load them first (`a.context.__pc = JSON.parse(fs.readFileSync('data/calibration.json')); a.run('PUBLIC_CALIB = __pc')`) or every build reads as "legacy" and the distinction under test disappears.
- jsdom cannot build the library sidebar dropdowns (they parse HTML through `DOMParser`): any test that reaches `renderLibrary` must stub it or `libDropdown`, or it fails inside `el()`.
- `npm run lint` lints `tests/*.mjs` too and rejects `innerHTML`/`outerHTML` assignment from a value (`UNSAFE_VAR_ASSIGNMENT`) — build replacement nodes with DOM APIs instead. It also lints the gitignored `tmp-ext-test/` scratch dir: a scratch file with a syntax error, or one written as UTF-16 by a PowerShell redirect, fails lint for the whole repo.
- Network code (`recent-games.js`) takes an injected `fetchImpl` — unit tests never touch the network.
- `npm run test:browsers` reads `web-ext-artifacts/latest-release.json`, so it needs a prior `npm run build` (it drives the *packaged* extensions, not the working tree).
- **Never assert a wall-clock budget in a test.** Files run in parallel, so a fixed millisecond limit fails on a busy machine with unchanged code (a fixed budget once failed in a full run and passed 3/3 alone). Measure a trivial call in the same run and scale the budget with it, or count work instead of time.

## Architecture
- **Single-file app logic**: `analysis.js` (~7770 lines) — state machine, classification, UI rendering, engine coordination
- **Automatic layout**: `lib/full-hd-layout.js` composes the view for the actual viewport at the browser's own zoom (ported from upstream's Full HD reference pass): the board takes the window height and the panels are **two** columns about 75% of the board's width (`S.settings.panelSizePct`, a Visual → Layout slider, clamped so they never overflow the window) — review on top, moves|accuracy, the graph under the move list, the engine under the accuracy, controls full width. Windows under 1100x520 fall back to the responsive CSS grid. The browser tab zoom is only fitted for a *custom* canvas (Reorganize); the auto layout gives a leftover fitted zoom back on the forced fit and otherwise leaves a manual zoom alone. A box may carry `scale`; `applyPanelBox` scales the module's `.mod-inner` by it — `fitEnginePanel`/`fitGraphFoot`/`accuracyReflowInfo` convert measurements back through that scale
- **Reorganize canvas (ported from upstream)**: entering Reorganize freezes the automatic composition into free-canvas boxes. Panels carry a ✓ selection toggle (or Ctrl/Cmd/Shift on a handle); one gesture engine (`makeMovable`) freezes the boxes at pointerdown and applies pure group transforms from `lib/panel-layout.js` (`movePanelGroup` / `scalePanelGroup` / `panelGroupBounds`) on every move, so selecting several panels drags/scales them as one (group bounds snap to the grid; a group keeps each member's offset ratio and content `scale`, clamped 0.25–4). The movable/minimizable layout toolbar holds the Grid select (`layoutGridSize`: 16 Standard default / 8 / 2, painted on the canvas via `--layout-grid-size`/`--layout-grid-major`), Right panels / All / Clear + count, Done, and Export (`chess-review-layout.json`, schema `chess-review-layout-v1`). Tests: `tests/panel-layout.test.mjs` (pure math), `tests/reorg-panels.test.mjs` (DOM)
- **Accuracy panel pages**: the panel is three pages — Accuracy / Move quality / Advanced — navigated by the retained rail from `lib/accuracy-navigation.js` (ported from upstream). The category rows only exist on the Quality page: code and tests that query `[data-category]` must call `setAccuracyPage(1)` first, and `accuracyReflowInfo` falls back to the stylesheet's row height when the rows are not mounted. The Quality page uses upstream's distribution design: a summary with each side's classified-move total and a per-category spectrum, and each category row paints its side's share behind the count (`--quality-color`, `--share-left`/`--share-right`, `[data-quality-segment]`, updated in place by `updateQualityShares`)
- **Eval graph styles**: `graphDesign` (upstream's set: original / timeline / bars / bars2 / bars3 default / bars4 / minimal) plus the classic curve in `graphStyle` (`area` / `line` / `color` / `minimal`); bars are one column per evaluated position, asinh-compressed from the analysed range (a 1-pawn advantage reaches the plot edge). Bar styles use a different x mapping (`fromFraction`, `toX`) for the hover marker and click-to-jump. **Fork deviation**: the bar slot span never drops below `BAR_SLOTS` (8), so a nearly empty game cannot stretch its few columns into slabs — on a fresh live board one +0.3 position used to fill a third of the plot as a white block. The colour design paints a white field above the boundary and a black one below (its own y-mapping, `toYc`)
- **Launch flow**: `analyze-flow.js` `openAnalysisTab()` is shared by popup click and the `Ctrl+Shift+Y` shortcut; it stashes the game under a per-job UUID key (`job:<uuid>`) and opens `analysis.html#<uuid>` (a timestamp alone collides across same-ms launches)
- **Live board** (`meta.live`): a real game played on the review board. `livePlayMove()` appends each move to the mainline PGN, so the graph/accuracy/Elo/phase estimates all come from the normal `computeDerived()` path — no second scoring pipeline. A move from an earlier ply still opens a variation; `undoLiveMove()` (controls-bar button, Ctrl+Z) pops only the move at the tip, only while the game is in progress, and drops that ply's `evals`/`bests`, re-stamps the PGN and re-requests the tail search. `requestLiveAnalysis()` also runs the shared `annotateKeyMoves()` after the tail search, so Great and a won-position Brilliant can appear during play even though the live search uses the panel's line count (usually 1). Resign/checkmate/draw calls `finishLive()`, which stamps `Result` + `meta.liveOver` and *stops*: the board keeps the live analysis and shows an "Analyse this game" button under the graph (`#graphFoot`, gated by `liveFinishPending()`), whose click runs `applyGame()` → `startAnalysis()` → `saveToLibrary()`; `meta.liveReviewed` stops it reappearing. Nothing is analysed or saved unprompted. It is deliberately NOT the review board: `activeBest()` returns the best line for the position *in view* (a review looks one ply back), the arrow is never suppressed for Book/Best, and `renderLive()` calls `refreshBoardAnnotations()` so the board badge, category tint and arrow appear as soon as the new search answers (a full `paintBoard()` would restart piece nodes mid-drag). Live searches are uncalibrated, so live accuracy/Elo can differ from the final public-scoring review on SF19 builds
- **Review rendering & navigation (perf work ported from upstream)**: `renderGraph()` draws contiguous *runs* and leaves pending positions empty, keeps its SVG and moves only `.eg-pos` when the plot is unchanged; `playersSignature()`, `UI.engineRenderKey` and `UI.libSig` skip rebuilding the player strips, engine panel and library list when nothing they show changed. `mainlineNavigationLimit()` lets navigation cross pending gaps up to the furthest published evaluation while the batch runs. Extra engine-panel candidate lines live in `panelLineCache` (16 entries, in-flight requests shared) and are **display-only, never scoring evidence**. Content scripts batch injections per frame; coach rigs skip unchanged SVG writes
- **Background warm-up (ported from upstream)**: after a review finishes, `schedulePanelPrecalculation()` starts ONE extra engine (Hash 16, the review's skill) that warms the extra engine-panel candidate lines for every position — the one in view first, then game order — pacing itself (idle ≈ 3× the search time, ~25% of one core). `panelPrecalcCount()` = max(`engineLines`, `classifyLines`), so a single line everywhere has nothing to warm. Any pointer/key/wheel, a hidden tab, a review (`startAnalysis` stops it), practice, a line walk, an in-flight panel request (`panelPending`) or live search (`S.liveEngine.current`) interrupts the current search; an interrupted result is discarded and the position retried (a partial search can never become evidence). Warmed lines land in `panelLineCache` (navigation is then instant) and, when they pass `annotationSearchFor`, in `S.bests[i].annotationSearch` — **display/badge evidence only, never scoring** — repainting and re-saving only when a category actually changes. `resetLiveEngine()` and engine-setting changes stop it. Tests: `tests/background-precalc.test.mjs`
- **Screen-size preview (ported from upstream)**: `screen-preview.html` + `lib/viewport-preview.js/css` render the real analysis app in an iframe sized to a chosen screen (Desktop/Laptop/Tablet/Phone/Custom presets, width×height, Rotate, Fit vs Actual view, full screen, hideable controls). The app inside loads `analysis.html?viewport-preview=1`: `main()` calls `installPreviewStorage()` first, which swaps `browserAPI.storage.local` for a memory adapter (`previewMemoryStorage`) seeded from the real stored values plus the launch snapshot — **nothing the preview does is ever saved**; `loadJob()` then returns the snapshot's game (or `PREVIEW_SAMPLE` on a direct visit). The launcher (`openScreenSizePreview()`, Layout settings) writes a one-shot `screen-size-preview` sessionStorage snapshot (job incl. a finished review's analysis, `S.idx`, display metrics, settings + `layoutForSave()`) that `window.open` copies synchronously and then removes; the viewer reads the same key for its "Current window" preset. The viewer iframe must NOT front the setup panel: the size tabs live inside the collapsed `#preview-settings`. Tests: `tests/viewport-preview.test.mjs`
- **WASM pool**: `engine/uci.js` wraps bundled Stockfish; `createEngine()` in analysis.js manages parallel workers
- **Native engine**: `engine/native.js` (`NativeEngine`, same contract as uci.js) ↔ `native/host/ChessReviewHost.exe` ↔ real Stockfish 19. Build key `native19` is tried only when selected; native falls back DOWN to WASM (`nnue` → `sf19full` → `sf19lite`), never the reverse, and the Engine tab shows the build that is really running ("… (fallback)")
- **Recent games**: `recent-games.js` pages through a user's games (30 per page via `createRecentGamesPager`; Lichess uses the export's `until`, Chess.com walks monthly archives) from the platform APIs by username (popup section "Recent games"). The popup remembers the names it has actually fetched in `recentUsers:<site>` (newest first, max 8, per site) and offers them as chips plus the field's `<datalist>`; only a fetch that returned games is stored, so a typo never comes back. **Do not expect the browser to autofill here**: a username-only field is never offered by a password manager, and browsers do not autofill extension popups reliably — the field carries `name`/`autocomplete` inside a real `<form>` because that is what the browser *would* need, but the extension's own list is the part that works
- **Game identity & caching**: `gameid.js` owns what makes two games "the same" (platform id, else a PGN hash) and every `gamecache:` key; `gamecache.js` stores fetched PGNs locally (LRU-capped) so re-opening a seen game costs no API calls
- **Save protection (ported from upstream)**: `saveToLibrary` keeps the review as a snapshot in `_pendingReviewSaves` until the library write lands. A failure leaves a floating "Retry saving" row (`UI.saveStatus`, `.review-save-status`) and arms a `beforeunload` warning; `updateLibrary` returns true/false so the retry knows. Tests: `tests/review-save-retry.test.mjs`
- **Coach interaction (ported from upstream)**: the rig iframe is transparent and must not capture input, so `bindCoachPointer()` observes the *parent* document: `coachHitTest()` flips the iframe to `pointer-events:auto` just to ask `document.elementFromPoint`, then probes the rig's `#figure` shape; a press shakes the coach, pointer movement within ~100px follows with the head/eyes (one `requestAnimationFrame`-coalesced message per paint). `resetCoachAnimation()` clears every pending animation on a switch/off, and the frame's `load` handler re-syncs talking state and checks the frame is still the mounted one. `elementFromPoint` does not exist in jsdom — stub it in tests. Tests: `tests/coach-interaction.test.mjs`
- **No build step for source** — the extension loads raw JS/CSS; `npm run build` only packages for stores
- **Reference docs**: `docs/MOVE_CLASSIFICATION.md` is the authoritative classifier policy (categories are annotations — they never move accuracy/rating); `docs/PERFORMANCE.md` records the baseline and how to compare `npm run perf` runs (only at a matching `--reps`)

## Classification traps (the badges that "disappear")
- **Great and a won-position Brilliant need a runner-up line** (`onlyGoodReply`, `brilliantEligible`), and the default review scores one line per position, so without help they can never fire and silently read as Best/Excellent. `classifyLine` records those plies in `state.annotationWanted`; `annotateKeyMoves()` runs one validated 2-line search at just those roots (max `KEY_MOVE_SEARCH_MAX`), called after the review batch and after each live tail search (`requestLiveAnalysis`). A restored review does **not** re-run it — that is what `ANNOTATION_VERSION` in the settings key is for. The result is stored as `annotationSearch`, which `annotationRoot()` uses at any Analysis-lines setting, and it never replaces the scored best/played pair. An attempted root is marked `annotationTried` so a live repaint cannot repeat a failed search — but a run the live board supersedes (the next move) un-marks the roots it never finished, or those plies could never earn the badge for the rest of the game. A one-line review's settings key includes `ANNOTATION_VERSION`, so a save from before this pass is re-analysed once instead of being restored without the categories. Do not "fix" a missing Great by loosening `onlyGoodReply` — it is the upstream rule
- **The same game can earn Brilliant on one build and none on another.** Brilliant additionally requires "not already completely winning" (`BRILLIANT_POLICY.clearlyWinningPawns = 5`): in a +7 position it needs the runner-up line to be under +5. Verified: Rotlewi–Rubinstein 1907 (`22...Rxc3`) is brilliant + great on the native SF19 exe at 20,000 nodes, and Best/Inaccuracy with the `sf19full` WASM build. Before changing a rule, check which build produced the evidence
- **Forced** is a first-class category keyed off `_forcedAt(i)` = *exactly one legal move in the position before* (a board fact, no eval). `classifyMove` returns it before any eval logic, so a forced move can never be Brilliant/Great/Blunder. It is deliberately **badge-only**: `catAcc("forced")` scores 100 like Best and `move-grades.js` grades it 9 like Best (accuracy/ratings unchanged), and it is absent from `QBREAK_SUMMARY`/`QBREAK_FULL` (an extra row resizes the accuracy panel and shifts the saved desktop canvas). The best-move arrow stays suppressed on it, exactly as when it read as Best
- **State object `S`** in analysis.js holds all mutable state — search for `const S = {`. `analysis.js` has no exports; tests execute it in a vm context and read the `S` global
- **Classification thresholds** live in `CALIB` (winK, clsWp) — tests inject overrides; the public models live in `data/calibration.json` and are read through `PUBLIC_CALIB`
- **Engine builds**: `ENGINE_BUILDS` (WASM paths) + `NATIVE_BUILD = "native19"`; `isKnownEngineBuild()` gates migration and cache restore — native/WASM analysis caches are separate

## Reusing a saved review (two gates, both easy to get wrong)
- `analysisSettingsKey()` decides whether a save matches the current settings. For an SF19 build it **omits depth/hash/strength** — correct only while that build can really run the fixed 20,000-node protocol. `nativeScoringPossible()` decides that, and it must treat "never started, and the probe says the helper is unavailable" as **not** able to score: a review would then fall back to a WASM build whose scores *do* depend on those settings, while the key pretended they could not change anything. A helper that has started answers for itself (`S.nativeScoring`), so an old probe can never deny a running engine its protocol.
- `canRestoreAnalysis()` also requires `savedReviewMatchesChosenBuild()`: the review must come from the build the user has selected **now**. The settings key pins the *chosen* build, which does not change when a helper is installed, so without this the WASM-scored review saved while Native was selected is restored for ever and the freshly installed native engine is never used. Older saves with no `engineBuild` still restore.

## UI traps
- **Module layout**: `.mod … > .mod-inner > div` forces `flex-direction: column` on every direct child of a module body. A row you add inside a module will silently wrap into a *second column* (this pushed the live board's button over the Engine panel) — style it by **id** or set `flex-direction: row` explicitly, and grow the module for the extra row the way `fitGraphFoot()` does for the live board's `#graphFoot`
- **Board frame** (`boardFrame` wood/accent + `coordsOutside`, Visual → Board / Pieces) is a *transparent `border`* on `.board` painted by a background gradient (`.board.framed` in styles.css), not a wrapper: absolutely positioned overlays (arrows, badges, promotion picker, the `.coords-out` labels) keep resolving against the padding box, so the playing area is unchanged. Any code measuring the board for pointer/drag geometry must use `boardInner()` (the padding box) instead of `getBoundingClientRect()` on the whole element, or the frame is counted as squares
- **CSS variables** for move quality: `--q-brilliant` through `--q-blunder` (Chess.com palette) plus `--q-forced` (light blue). Piece sets: only `cburnett` and `merida` are packaged (GPLv2+)
- Extension CSP requires `'wasm-unsafe-eval'` for Stockfish WASM. No TypeScript, no bundler — plain ES modules

## Progress page & backup (fork-native, not upstream)
- The Progress page reads only `browserAPI.storage.local["library"]`, and reports on **one account**: the handle in `storage.local.username` (popup → Manual setup → Username, the same value that seats a review). `ownGames()` in `lib/progress.js` keeps only that account's games and re-points the `my*` fields when a record was saved from the opponent's seat (swapping accuracy/rating/names, inverting `result`, dropping `myPhases` since the opponent's per-phase numbers are not stored). With no handle set the page shows the whole library **and says so** — never silently mixing other people's games into "my progress". `progress.js` follows `storage.onChanged` so saving a handle updates an open page
- Per-phase accuracy and personal bests depend on records saved *after* `saveToLibrary` began writing `plies` + `myPhases`, so older records are skipped (the reports tolerate missing fields)
- The seat/orientation rule is **shared** (`lib/library-seat.js`), used by both `progress.js` `openGame` and the analyzer's `openLibraryGame`, so the two doors into a saved game seat it identically — a record saved from the opponent's seat opens facing the tracked account, which is what makes a `move N` link land on that account's move (the analyzer imports it, so `tests/helpers/app.mjs` must keep injecting it). `dailyActivity` splits dated games outside its window into `older` (ordinary history) and `later` (a PGN timezone ahead of this one) so the tracker can never say "no games" while the cards count one
- Interactive layer: a KPI card that names a `metric` is a button that opens the evidence panel (`metricEvidence` — the rule, the statistics and the games behind the number). The daily tracker draws 12 weeks of day cells; clicking one scopes every report to that day (`filterGames({ day })`, a clearable chip). Rows and cells deep-link through `openAnalysisTab`; each saved game carries `myWorst`/`opWorst` (`{ ply, cat }`) so a row opens the review *at that move*: `applyGame` reads `meta.startPly` once and strips it, so it is never saved or replayed from the tab session
- Three more ways in, all through `scopeTo()` (set a filter + jump back to the overview) or `applyTarget()`: **What to work on** (`focusAreas` — weakest phase, costliest error type, weaker colour, losing opening, nemesis, each with a review-at-a-move or page scope), **Head to head** (`opponentReport`) and **Every game** (`gameRows`, sortable, one row per game with a `move N` button). A rival/opening/day scope is just another filter, so each shows as a clearable chip and `Reset filters` clears all of them. Placeholder names (`White`/`Black`, the Live board's own seats) count as `unnamed` by `opponentKey`, never as a rival
- `lib/library-backup.js` deliberately excludes the per-game analysis caches (`analysis:<id>`) and `gamecache:*` — they are large and rebuild on demand, keeping a 1000-game backup a few hundred KB
- `progress.html` carries its **own** design system (tokens in `:root`, then components) — it does not load `styles.css`, so a class used by `progress.js` must be defined there. Two traps: `el()` must set `--custom-properties` with `setProperty` (`Object.assign` drops them silently), and `svg()` must attach `on*` values as listeners (`setAttribute` stringifies them into an inline attribute that never runs). The sticky header and chip rows wrap, so `syncStickyOffset()` measures both into `--top-h`/`--sticky-h`, which drive the toolbar's `top` and every section's `scroll-margin-top` (a hard-coded offset hid the heading a jump landed on)
- `saveToLibrary` names the analyzed seat after the tracked handle when the PGN has no player headers (`savedName`): a record saved as `White`/`Black` can never be matched to an account, so the game would silently vanish from Progress
- Two report invariants: `progressPoints` reports **one** rating scale per window (`ratingScale` picks the review's estimate or the recorded Elo, whichever covers more games — never averaged together, and `summarizeProgress` reports `missingRating`), and `personalBests` counts streaks over `streakSource` (every tracked game) so a Result/colour/format filter cannot turn unrelated wins into a run

## Packaging & lint
- `scripts/package.mjs` uses an **explicit allowlist**: top-level files (`files`) and whole directories (`directories`: `lib`, `data`, `engine`, …) are copied by name, so a new **top-level** file a page/script imports MUST be added or the store ZIPs break (this bit `recent-games.js`); a new file under a listed directory ships automatically
- `native/` goes into the **source snapshot only**, never the browser ZIPs; `scripts/lint.mjs` skips `.git`, `node_modules`, `web-ext-artifacts`, `calibration-runs`, `native`, `manifest.json` — but **not** the gitignored `tmp-ext-test/` scratch dir, so keep scratch files valid and UTF-8
- `manifest.version` must equal `package.json` `version` or the build throws

## Native engine (Windows)
- SF19 scoring family: `lib/scoring-builds.js` (`sf19lite`, `sf19full`, `native19`) — one protocol (fixed 20,000 nodes, Hash 32, UCI_ShowWDL, exact-only, restricted-move searches). Native needs host ≥ 1.1.0 (`hello.capabilities` contains `scoring-v1`); `S.nativeScoring === false` means an old helper and the legacy path. Never hard-code `sf19lite`; use `isSf19Build`
- **Installing is the one `.bat`; the extension has no download button, deliberately.** There used to be a "Download installer (.zip)" that opened `T-Julsgaard/Chess-Review/releases/latest/download/ChessReview-NativeEngine-Windows.zip` — a 404 for its entire life, because **upstream publishes no releases at all** and this fork's only release carries no such asset. A later change only made it print the dead link. Do not reintroduce any click for it: a browser page cannot run an installer or register a host, so `nativeStatusRow` names `Install Native Engine.bat` and offers only **Recheck** and **Diagnostics** (both work). `tests/native-engine.test.mjs` asserts the row has no links and no inline handlers
- `Install Native Engine.bat` (repo root) → `native/install.ps1`, and it is self-sufficient: with no `native/` it first fetches `install.ps1`, the helper source, the prebuilt helper and both `checksums.json` from `raw.githubusercontent.com/aciokie/Chess-Review/main`, so **a bare copy runs whatever is on `main`, not the installer beside it**. It forwards its arguments (`-Force`, `-ExtensionId`, `-EnginePath`), and `native/uninstall.ps1` is the only supported removal
- The installer prefers the engine in `native/engine`, and when that copy is missing it **downloads the official Stockfish 19** (`official-stockfish` `sf_19` → `stockfish-windows-x86-64-universal.zip`), unpacks it and verifies it against `native/engine/checksums.json` before installing (a fresh download is byte-identical to the pinned hash). A download with no recorded hash to check against is **refused** — never install an unverified engine. `-NoEngineDownload` refuses the download outright for offline installs
- **A repeat run must do nothing.** `install.ps1` section 0 (`Test-InstallCurrent` + `Get-HelperIdentity`, recorded as `helperId` in `config.json`) checks the installed helper, its config, the pinned engine and every browser registration, and exits in well under a second when they all match: no `csc`, no 103 MB copy, no process started. This is the antivirus fix — a freshly compiled unsigned exe is a stranger to AV on every run, which is also why a **prebuilt `native/host/ChessReviewHost.exe` is committed** and pinned in `native/host/checksums.json` (stable bytes accumulate reputation). `-Force`, or any explicit option, does the full install and self-test
- Rebuilding the helper: build with the in-box `csc.exe` command recorded in `native/host/checksums.json` and **re-record the SHA-256**. A csc build is not reproducible (fresh module GUID and timestamp), so the hash pins the committed bytes — verify by comparing it, never by rebuilding and expecting a match. `.gitattributes` keeps it byte-exact (`native/host/*.exe binary`)
- **Extension ids**: `Find-UnpackedExtensionIds` reads the browser profiles and accepts the folder the installer ran from **or any folder inside it** (so a staging dir or worktree copy is registered). A brand-new profile has not yet written where the extension was loaded from, so detection can miss it — the Build row then prints the exact command, `Install Native Engine.bat -ExtensionId <id>` (the extension knows its own id via `browserAPI.runtime.id`; nothing else can tell the user). The Chrome Web Store id is always allowed, so store installs never need this
- `native/README.md` is stale where it says "Nothing is downloaded at install time" and "You do **not** need to download one": the installer now fetches the official build when the bundled copy is absent, and it does not mention the no-op preflight. Trust `install.ps1`
- `csc.exe` (in-box .NET Framework 4.8) only speaks **C# 5**: no string interpolation, no `?.`, no `catch … when`
- **PowerShell 5.1 rules**: keep `.ps1` files pure ASCII + UTF-8 BOM (BOM-less files decode as ANSI and smart quotes inside strings break parsing); `New-Item -Force` fails on missing registry keys (guard with `Test-Path`); `Dictionary<K,V>` has no string `Contains()` — use `ContainsKey`. Test the installer by running it; it is the only way to catch a quoting or label mistake
- Non-git installs update via `Update Extension.bat` → `update-extension.ps1` (diffs GitHub, downloads only changed files); it follows the same PS 5.1 rules

## Engine Verification
- `npm run verify:engines` checks SHA-256 in `engine/` against `engine/checksums.json`, which pins 6 files — SF18 NNUE (`stockfish-nnue.js/.wasm`), SF19 **Lite** (`stockfish-19-lite-single.js/.wasm`) and SF19 **Full** (`stockfish-19-single.js/.wasm`, build key `sf19full`). This pins the *committed bytes* only: it proves the working tree has not drifted from what was committed, **not** that those bytes came from the official Stockfish release
- `.gitattributes` keeps hash-pinned binaries byte-exact: `engine/stockfish*.js -text`, `engine/*.wasm binary`, `native/engine/*.exe binary`, `native/host/*.exe binary`. Never reformat, re-save or hand-regenerate any of them, or the checksums stop matching. It also pins `tools/calibration/public/*.json text eol=lf` (those models are hashed over their LF bytes, so `core.autocrlf` would make `reproduce-public.mjs` fail on Windows) and `*.bat text eol=crlf` (a GitHub ZIP download does not run through `core.autocrlf`, and cmd can mis-parse a `.bat` that arrives with bare LF)
- Native: engine exe pinned in `native/engine/checksums.json` (auto-verified + hash-pinned at install); prebuilt helper pinned in `native/host/checksums.json`. The bundled native engine is ~103 MB — GitHub warns >50 MB (hard limit 100 MB); use Releases, not LFS, if it ever needs to move

## Real-browser & real-engine testing
- Unpacked extensions need `playwright-core` + `chromium.launchPersistentContext` with `--load-extension` and an isolated profile dir per run — the Playwright MCP browser cannot load unpacked extensions
- `analysis.html` loads `analysis.js` as `type="module"`, so `page.evaluate` can **not** reach `S`: assert through the DOM and `chrome.storage.local`. Categories are published as `data-class` on `.ml-move[data-ply]` — read those, not the innerText
- Drive a full review without clicking: seed `job:<id>` (`{ pgn, meta }`) from an extension page, then open `analysis.html#<id>`. Read back the persisted `analysis:<id>` record for `settingsKey`/`annotationSearch`/`engineBuild`
- Two traps that cost real time: **`page.goto` to the same document with only a different `#hash` does not reload it** (the app keeps running the previous payload — open a new page, or go via `about:blank`), and the `job:<id>` handoff is **one-shot** (its sessionStorage copy dies with the tab), so re-seed it to reopen the same game
- Testing the native path is a journey, and the only honest way to run it is end to end: `native/uninstall.ps1` (removes the registry key and `%LOCALAPPDATA%\ChessReview`), a fresh profile, the **packaged** extension (the store build has no `native/`), read the Build row, run the .bat, press **Recheck**, then review. Assert `engineBuild` on the persisted record — `"nnue"` while only the fallback could run, `"native19"` once it is connected
- `opencode.json` holds a `PLAYWRIGHT_MCP_EXTENSION_TOKEN` secret — never `git add` it (it is in `.gitignore`). It runs the Playwright MCP with `--extension` against the local **Brave** (`PLAYWRIGHT_MCP_EXECUTABLE_PATH`); that bridge controls your own browser, it does not launch one with `--load-extension`
- **Lichess 404s `HeadlessChrome` user agents** on its API — set a normal Chrome `userAgent` in the test context or live fetches fail with "user not found"
- MV3 service workers idle out (~30 s): seed storage through an extension **page** context, not a captured worker
- `npm run test:browsers` uses packaged ZIPs + isolated profiles; it falls back to `C:\Program Files\Google\Chrome\Application\chrome.exe` / `C:\Program Files\Mozilla Firefox\firefox.exe` unless `CHROME_PATH` / `FIREFOX_PATH` is set. This machine has **Brave only**, so pass `CHROME_PATH` or the Chrome half fails; the Firefox half cannot run at all
- **A real engine can run in Node too**: `native/engine/stockfish-windows-x86-64-universal.exe` speaks plain UCI, so a child-process UCI client can produce real scoring roots and feed them to the real classifier in the vm harness (no browser needed). `tmp-ext-test/` is the gitignored scratch dir for these — keep throwaway scripts there (a plain `git add -A` once committed them), but remember `npm run lint` lints it

## Workflow & environment
- This is a fork of `T-Julsgaard/Chess-Review` (the public upstream). `README.md`, `CONTRIBUTING.md`, `.github/pull_request_template.md`, `.github/ISSUE_TEMPLATE/` and `.github/dependabot.yml` describe the upstream contribution flow
- **Always commit and push.** A verified change is not done until it is on `main`: commit and push it in the same turn, without waiting to be asked, and never leave verified work sitting uncommitted. Push straight to `main` (this repo's convention; no PR flow) and never push upstream
- When asked to *audit/check* something, stay read-only — report findings and wait for an explicit go-ahead before editing
- `git push` writes to stderr, so PowerShell reports exit code 1 even on success — verify the `old..new main -> main` line instead
- `Set-Content -Encoding UTF8` writes a BOM, which lands in the commit subject when you use `git commit -F` — use `-Encoding ascii` (or the write tool) for message files. In the other direction, `npm test > file.txt` and `git show` redirected by PowerShell write **UTF-16**, so read those files back as `utf16le` (or just pipe through `node`) instead of grepping them
- This machine has **no VM tooling** (no VirtualBox/VMware/QEMU/Docker/Hyper-V; WSL cannot drive a Windows native-messaging host), so a "new user" test is: uninstall + fresh profile + packaged extension + real install. Say so rather than claiming a VM
- This machine runs Avast: freshly compiled exes get scanned (slow cold starts, occasional `EPERM` on `Process.Start` — the host already retries). Anything that recompiles or relaunches a helper on every run will wake it every time
- Long `node -e "..."` one-liners get mangled by the shell here — write a temp `.cjs`/`.mjs`/`.ps1` script file instead
- Other sessions push to `main`; `git fetch` before starting new work
